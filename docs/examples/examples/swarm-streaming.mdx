## What This Example Shows

- How to enable swarm-level streaming with `stream: true` on `/v1/swarm/completions`
- The full SSE event sequence for swarms: `metadata`, `start`, `status`, `chunk`, `usage`, `end`, `done`, and the `error` event sent on failure
- How to read the swarm's output from the single `chunk` event
- How to split that output into one panel per agent
- Why this differs from single-agent streaming on `/v1/agent/completions`

<Info>
Single-agent streaming (covered in [Streaming Responses](/docs/examples/examples/streaming)) streams one model's tokens as they are generated. Swarm streaming does not stream tokens: the swarm runs to completion on the server, then its whole output arrives in one `chunk` event. Every swarm type, including `SequentialWorkflow` and `AgentRearrange`, sends the same events in the same order.
</Info>

## Why This Matters

A swarm run can take a while, and a request without `stream` returns nothing until it is over. With `stream: true` you get the `job_id`, swarm type and agent count as soon as the request is validated and its agents are built, a `status` event with the input token count just before the swarm starts, then the output, the token usage and the cost as separate events. That is enough to show progress and a cost line in a UI, with one parser for every swarm type. If you need text to appear while it is being generated, stream a single agent on `/v1/agent/completions` instead.

## Step 1: Setup

```python
import json
import os

import requests
from dotenv import load_dotenv

load_dotenv()

API_KEY = os.getenv("SWARMS_API_KEY")
BASE_URL = "https://api.swarms.world"

# X-Accel-Buffering: no disables proxy buffering so tokens flush immediately.
headers = {
    "x-api-key": API_KEY,
    "Content-Type": "application/json",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",
}
```

## Step 2: Understand the SSE Event Types

When `stream=true` is set on **any** swarm type, `/v1/swarm/completions` responds with a Server-Sent Events stream instead of a JSON body — the HTTP status is `200` even if the swarm run later fails, so failures show up as an `error` event, not an HTTP error code. Each event has an `event:` line and a `data:` JSON payload. This is the exact event sequence emitted by `api/swarm_streaming.py`:

| Event | Emitted | Payload (key fields) |
| --- | --- | --- |
| `metadata` | Once, at the start | `job_id`, `status: "initializing"`, `swarm_name`, `description`, `swarm_type`, `number_of_agents`, `timestamp`, `stream: true` |
| `start` | Once, right after `metadata` | `message: "Starting swarm processing..."` |
| `status` | Once, after agents and the router are built | `status: "executing"`, `message`, `input_tokens`, `timestamp` |
| `chunk` | Once, after the whole swarm has finished | `output` (the same value the non-streaming response returns under `output`), `timestamp` |
| `usage` | Once, near the end | `input_tokens`, `output_tokens`, `total_tokens`, `total_cost`, `billing_info` (the same cost-breakdown object the non-streaming response nests under `usage.billing_info`) |
| `end` | Once, terminal on success | `job_id`, `status: "success"`, `execution_time`, `timestamp`, `complete: true`, plus `tasks`/`messages` if the request included them (does not include the output; read it from the `chunk` event) |
| `done` | Once, always last on success | `message: "Swarm processing complete"` |
| `error` | Instead of the rest, if anything in the generator raises | `error` (string, prefixed `"SwarmCompletionError: "`), `timestamp` |

<Warning>
`chunk` has one shape for every `swarm_type`: `{"output": ..., "timestamp": "..."}`, sent exactly **once**. There is no per-token `chunk`, no `content` or `agent` field, and no `agent_start` or `agent_end` event, so no text arrives while the agents are working. A request with `tasks` instead of `task` also gets one `chunk`, carrying the batch result.
</Warning>

<Note>
For the `SequentialWorkflow` run below, `output` is the swarm's conversation: a list of messages, each with the agent's name as `role` and its text as `content`, for example `[{"role": "Researcher", "content": "..."}, {"role": "Writer", "content": "..."}]`. Your own task is not included. It is the same value the request returns under `output` without `stream`, and `usage` reports the same tokens and cost.
</Note>

## Step 3: Stream a `SequentialWorkflow`

In a sequential swarm, agents run one after another. The stream reports progress up to `status`, stays quiet while both agents run, then delivers both agents' messages together in the one `chunk`.

```python
def make_agent(name, system_prompt):
    return {
        "agent_name": name,
        "system_prompt": system_prompt,
        "model_name": "gpt-4.1-mini",
        "role": "worker",
        "max_loops": 1,
    }


def stream_sequential():
    payload = {
        "name": "streaming-sequential-example",
        "swarm_type": "SequentialWorkflow",
        "task": "List two short bullets about solid-state batteries.",
        "stream": True,
        "max_loops": 1,
        "agents": [
            make_agent("Researcher", "List two short bullets on the topic."),
            make_agent("Writer", "Combine the bullets into one short paragraph."),
        ],
    }

    response = requests.post(
        f"{BASE_URL}/v1/swarm/completions",
        headers=headers,
        json=payload,
        stream=True,
        timeout=120,
    )
    response.raise_for_status()

    event_name = None
    for line in response.iter_lines(decode_unicode=True):
        if not line:
            continue
        if line.startswith("event:"):
            event_name = line[len("event:"):].strip()
            continue
        if line.startswith("data:"):
            try:
                data = json.loads(line[len("data:"):].strip())
            except json.JSONDecodeError:
                continue
            if event_name == "status":
                print(f"[status] {data.get('message')}, input_tokens={data.get('input_tokens')}")
            elif event_name == "chunk":
                for message in data.get("output") or []:
                    print(f"\n--- {message.get('role')} ---\n{message.get('content')}")
            elif event_name == "usage":
                print(f"\n[usage] total_tokens={data.get('total_tokens')} total_cost={data.get('total_cost')}")
            elif event_name == "end":
                elapsed = data.get("execution_time")
                print(f"\n[end] {elapsed:.2f}s" if elapsed else "\n[end]")
            elif event_name == "error":
                print(f"\n[error] {data.get('error')}")


if __name__ == "__main__":
    stream_sequential()
```

You'll see the `[status] Running 2 agents, input_tokens=...` line, a pause while the Researcher and then the Writer run, then both sections at once, followed by the usage and `[end]` lines.

`AgentRearrange` streams the same way. Set `"swarm_type": "AgentRearrange"` and a `rearrange_flow` such as `"Researcher -> Writer"`, and the loop above works unchanged.

## Step 4: Rendering Each Agent's Output in a UI

In a real UI you want each agent's output in its own panel. The `chunk` event carries every agent's message, so bucket the messages in `output` by `role`:

```python
def render_per_agent(response):
    panels: dict[str, str] = {}
    current_event = None
    for line in response.iter_lines(decode_unicode=True):
        if not line:
            continue
        if line.startswith("event:"):
            current_event = line[len("event:"):].strip()
        elif line.startswith("data:"):
            data = json.loads(line[len("data:"):].strip())
            if current_event == "chunk":
                for message in data.get("output") or []:
                    role = message.get("role", "unknown")
                    panels[role] = panels.get(role, "") + str(message.get("content") or "")
            elif current_event == "end":
                break
    return panels
```

The single `chunk` becomes one text buffer per agent, which is what a multi-panel UI needs. An agent that speaks more than once, for example with `max_loops` above 1, gets its messages appended to the same panel.

<AccordionGroup>
  <Accordion title="Which swarm types support `stream=true`?">
    `stream: true` is accepted for every `swarm_type`, and every type streams the same way, `SequentialWorkflow` and `AgentRearrange` included. The swarm runs to completion server-side first, then the entire result is sent as a single `chunk` event (`{"output": ..., "timestamp": ...}`). You still get the `metadata`/`start`/`status`/`usage`/`end`/`done` events around it, so streaming is useful for status updates and cost, just not per-token text.
  </Accordion>
  <Accordion title="Why isn't my stream actually streaming?">
    Two common causes: (1) you forgot `stream=True` on the `requests.post` call (the API streams but your client buffers the whole response), or (2) a reverse proxy is buffering. Set `X-Accel-Buffering: no` in your request headers and make sure your client reads with `response.iter_lines()`, not `response.text`.
  </Accordion>
  <Accordion title="How do I know when an individual agent is finished vs. the whole swarm?">
    There is no per-agent event. Every agent has finished by the time the `chunk` event arrives, and each agent's message is in its `output`. `end` fires once for the entire swarm after usage is reported, followed by a final `done` event. Fill per-agent panels from the `chunk`; dismiss a global spinner on `end` or `done`.
  </Accordion>
  <Accordion title="How do I handle errors mid-stream?">
    The HTTP response starts with a `200` as soon as the stream opens, before the swarm has actually run — so a failure never shows up as a non-200 status. Instead, the generator catches the exception and emits a single `event: error` with `{"error": "SwarmCompletionError: ...", "timestamp": "..."}`, then the stream ends without `usage`/`end`/`done`. Always watch for `event: error` in your parser, not just HTTP status codes.
  </Accordion>
</AccordionGroup>
